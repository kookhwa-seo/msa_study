# 블로킹 vs 논블로킹 외부 API 호출 실습

## 구성

- **`mock-payment-gateway`**(포트 8087): 진짜 카드사/PG망을 흉내 내는 독립 서버. `POST
  /api/mock-payment/authorize`가 요청마다 200~500ms 랜덤 지연 후 승인 결과를 돌려준다. 이
  프로젝트의 Saga 참여자와는 무관하다 - 실제로도 결제망은 이 프로젝트 밖의 "진짜 외부" 시스템
  이므로, REST로 직접 호출해도 "서비스 간 직접 REST 호출 금지" 원칙(Saga 참여자 사이의 원칙)과
  충돌하지 않는다.
- **`http-client-lab`**(포트 8088): 같은 mock 서버를 두 방식으로 부르는 비교 앱.
  - `POST /blocking` — `RestClient`로 동기 호출. 응답이 올 때까지 요청을 맡은 Tomcat 스레드가
    묶인다.
  - `POST /nonblocking` — `WebClient`로 비동기 호출하고 `Mono<String>`을 그대로 반환한다.
    Spring MVC가 리액티브 반환 타입을 서블릿 비동기 처리로 자동 전환해줘서, 응답을 기다리는
    동안 Tomcat 스레드가 풀로 반납된다.
  - 둘 다 같은 Tomcat(플랫폼 스레드 풀, 기본 200개)에서 돈다 - 차이는 "대기 중에 스레드를
    붙잡고 있느냐"뿐이다.

## 실행 방법

```bash
./gradlew :mock-payment-gateway:bootRun
./gradlew :http-client-lab:bootRun
BASE_URL=http://localhost:8088 TARGET_PATH=/blocking VU_COUNT=200 \
  k6 run infra/k6/http-client-comparison.js
```

## 실제 실행 결과

VU(동시 사용자) 수를 50/100/200/500으로 각각 20초씩 고정해서 측정했다(Tomcat 스레드 풀
기본값 200개).

| 동시 사용자 | 블로킹(RestClient) TPS | 블로킹 p99 | 논블로킹(WebClient) TPS | 논블로킹 p99 |
|---|---|---|---|---|
| 50  | 138.0 req/s | 504ms | 138.5 req/s | 503ms |
| 100 | 278.0 req/s | 502ms | 278.3 req/s | 502ms |
| 200 | 556.6 req/s | 501ms | 555.5 req/s | 501ms |
| **500** | **555.7 req/s** | **1,040ms** | **1,380.0 req/s** | **505ms** |

에러율은 전 구간 0%였다(블로킹도 실패하지 않고 요청이 쌓이기만 했다 - 아래 설명 참고).

## 왜 블로킹 방식이 동시 요청이 많아질수록 더 급격히 느려지는가

**동시 사용자가 200 이하일 때는 둘의 차이가 없다.** Tomcat 스레드 풀이 200개라, 동시 요청이
그 이하면 모든 요청이 각자 스레드를 하나씩 받아서 블로킹이든 논블로킹이든 응답 시간(200~500ms
지연 그대로)에 차이가 안 난다.

**동시 사용자가 500명(풀 크기 200개를 초과)이 되는 순간부터 갈린다.** 블로킹 방식은 요청 하나가
외부 응답을 기다리는 동안 스레드를 통째로 쥐고 있어서, 동시에 처리할 수 있는 요청이 딱 200개로
막힌다. 나머지 300명은 Tomcat의 **요청 큐**에서 스레드가 빌 때까지 기다려야 한다 - 그래서 TPS는
556 근처에서 더 못 올라가고(스레드 200개가 200~500ms마다 한 번씩 처리하는 게 물리적 한계),
그 대신 대기 시간만큼 p99가 501ms → 1,040ms로 거의 2배가 됐다. 에러가 안 난 건 Tomcat이 요청을
버리지 않고 큐에 쌓아뒀다가 순서대로 처리했기 때문인데, 사용자 입장에서는 "실패하진 않지만
계속 느려지는" 상황이 된다 - 진짜 장애 상황에서 흔히 보는 패턴이다.

논블로킹 방식은 스레드가 응답을 기다리지 않고 즉시 반납되니, 같은 200개 스레드로도 훨씬 많은
요청을 "돌려가며" 처리할 수 있다 - 그래서 500명이 몰려도 TPS가 계속 늘고(1,380 req/s, 블로킹의
2.5배) p99도 거의 그대로다.

## 핵심

블로킹 방식의 한계는 "느린 외부 서버를 기다리는 동안 내 스레드가 묶여서, 그 스레드 개수만큼만
동시 처리할 수 있다"는 것이다. 스레드는 개당 메모리(기본 스택 1MB)도 쓰고 OS가 관리하는 값비싼
자원이라 무한정 늘릴 수 없고, 결국 풀 크기가 곧 "이 서버가 동시에 버틸 수 있는 느린 외부
호출의 최대 개수"가 된다. 논블로킹은 그 제약 자체를 없앤다 - 이 실습에서 실측한 차이를 다음
실습(가상 스레드, `docs/virtual-thread-http-lab.md`)에서 코드를 하나도 안 바꾸고 다른 방법으로
풀 수 있는지 이어서 확인한다.
