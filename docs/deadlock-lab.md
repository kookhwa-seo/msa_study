# DB 트랜잭션 데드락 재현·방지 실습

## 왜 하는 실습인가

이 프로젝트는 지금까지 한 트랜잭션이 한 번에 행 하나만 잠그는 코드만 짜봤다(예: 결제 하나
저장, 차량 하나 배정). 그런데 실무에서는 하나의 트랜잭션이 **여러 행을 순서대로 잠그는**
코드가 흔하고, 그 순서를 맞추지 않으면 데드락이 난다. 이 실습은 이 프로젝트가 실제로 쓰는
vehicle-db(Postgres)에서 그 상황을 직접 만들어보고, Postgres가 이를 어떻게 탐지·해결하는지,
그리고 코드에서 락 순서를 통일하는 것만으로 왜 문제가 완전히 사라지는지 확인한다.

## 코드 위치

`deadlock-lab` 모듈 (`deadlock-lab/src/main/java/com/msastudy/deadlocklab/DeadlockLabRunner.java`).
`kafka-lab`과 같은 원칙으로 Spring/JPA 없이 순수 JDBC로 작성했다 — `SELECT ... FOR UPDATE`
행 락과 Postgres의 데드락 탐지를 코드 레벨에서 직접 다루기 위함. 실제 vehicle-service가 쓰는
`vehicle` 테이블을 그대로 대상으로 삼는다(별도 스키마를 새로 만들지 않는다).

## 실습 설계

vehicle 테이블에서 아무 행이나 2개(차량A, 차량B)를 골라서, 두 트랜잭션(tx-1, tx-2)이 각각
`SELECT ... FOR UPDATE`로 행을 하나씩 잠근다.

- **`broken` 모드**: tx-1은 차량A → 차량B 순서로, tx-2는 차량B → 차량A 순서로 잠근다(반대
  순서). `CyclicBarrier`로 "둘 다 자기 첫 번째 락을 잡을 때까지" 동기화한 다음 동시에 두
  번째 락을 시도하게 만들어서, 서로가 상대방이 들고 있는 행을 기다리는 순환 대기(circular
  wait)를 확정적으로 만든다.
- **`fixed` 모드**: tx-1, tx-2 모두 차량A → 차량B 순서로만 잠근다. 둘 다 같은 행을 먼저
  요청하니 하나가 먼저 잠그면 나머지는 그냥 "차례를 기다리는" 정상적인 락 대기 상태가
  되고, 순환 대기 자체가 성립할 수 없다. (이 모드에서는 broken 모드에서 쓴 barrier 동기화를
  쓰지 않는다 — 쓰면 뒤에 온 스레드가 첫 락도 못 잡은 채 barrier에서 영원히 기다리게 되어
  테스트 코드 자체가 멈춰버린다.)

## 실행 방법

```bash
docker compose up -d vehicle-db
# vehicle 테이블에 행이 있어야 한다 (없으면 vehicle-service를 한 번 기동해서 재고를 시딩)
./gradlew :deadlock-lab:run --args="broken"
./gradlew :deadlock-lab:run --args="fixed"
```

## 실제 실행 결과 (로그 발췌)

### broken 모드 — 실제 데드락 발생

```
대상 차량: A=1111010100-COMPACT-1, B=1111010100-COMPACT-2
[tx-2] 1차 락 획득: 1111010100-COMPACT-2
[tx-1] 1차 락 획득: 1111010100-COMPACT-1
[tx-1] 2차 락 시도: 1111010100-COMPACT-2   (tx-2가 들고 있음)
[tx-2] 2차 락 시도: 1111010100-COMPACT-1   (tx-1이 들고 있음)  <- 여기서 순환 대기 성립
[tx-1] 2차 락 획득: 1111010100-COMPACT-2 (1003ms 대기)
[tx-1] 커밋 완료 - 정상 종료
[tx-2] Postgres가 데드락을 탐지해서 이 트랜잭션을 강제 중단시킴: ERROR: deadlock detected
==================== 결과 (broken mode) ====================
전체 소요 시간: 1038ms
```

두 트랜잭션이 순환 대기에 들어간 지 약 1초(Postgres의 기본 `deadlock_timeout` 설정값) 뒤,
Postgres가 스스로 데드락을 탐지해서 두 트랜잭션 중 하나(tx-2)를 `SQLState 40P01`
(`deadlock detected`) 오류로 강제 종료시켰다. 살아남은 tx-1은 정상적으로 커밋됐다. **어느
쪽이 희생되는지는 Postgres 내부 판단(보통 더 적은 작업을 되돌리는 쪽)이라 실행마다 달라질
수 있다.**

### fixed 모드 — 데드락 없음, 그냥 순서대로 처리

```
대상 차량: A=1111010100-COMPACT-1, B=1111010100-COMPACT-2
[tx-1] 1차 락 획득: 1111010100-COMPACT-1
[tx-1] 2차 락 시도: 1111010100-COMPACT-2
[tx-1] 2차 락 획득: 1111010100-COMPACT-2 (0ms 대기)
[tx-1] 커밋 완료 - 정상 종료
[tx-2] 1차 락 획득: 1111010100-COMPACT-1   (tx-1이 이미 커밋해서 즉시 획득)
[tx-2] 2차 락 시도: 1111010100-COMPACT-2
[tx-2] 2차 락 획득: 1111010100-COMPACT-2 (0ms 대기)
[tx-2] 커밋 완료 - 정상 종료
==================== 결과 (fixed mode) ====================
전체 소요 시간: 25ms
```

두 트랜잭션 모두 성공했고, 전체 소요 시간도 1038ms → 25ms로 확 줄었다(데드락 탐지를 위한
1초 대기 자체가 없어졌기 때문). tx-2가 차량A를 요청했을 때 이미 tx-1이 커밋을 끝낸 뒤라
대기 없이 바로 락을 얻었다 — 두 트랜잭션이 겹치지 않고 순서대로(직렬로) 처리된 것이다.

## 결론 / 실무 연결

- 데드락은 "버그"라기보다 **여러 트랜잭션이 여러 자원을 서로 다른 순서로 잠글 때 생기는
  구조적 위험**이다. 코드 자체는 각자 아무 문제 없어 보여도, 두 코드 경로가 동시에 실행될
  때만 드러난다 — 그래서 로컬에서 순차 테스트만 돌려서는 절대 못 잡는다.
- Postgres(그리고 대부분의 관계형 DB)는 데드락을 스스로 탐지해서 한쪽을 강제로 롤백시키는
  안전장치를 갖고 있다 — 그래서 DB 전체가 멈추지는 않는다. 하지만 롤백당한 트랜잭션은
  애플리케이션이 재시도하거나 사용자에게 실패로 보여야 하고, 탐지까지 걸리는 시간
  (`deadlock_timeout`, 기본 1초)만큼 응답이 느려진다 — 트래픽이 몰릴수록 이 지연이 체감된다.
- 해결책은 복잡한 락 라이브러리가 아니라 **"여러 행을 잠글 때는 항상 정해진 순서(예: PK
  오름차순)로 잠근다"는 규칙 하나**다. fixed 모드가 보여주듯, 이 규칙만 지키면 순환 대기
  자체가 수학적으로 불가능해진다.
- 이 프로젝트에는 지금 이런 다중 행 잠금 코드가 없어서 실제로 이 위험에 노출돼 있지는
  않다. 이 랩은 "왜 없어도 되는지"가 아니라 "앞으로 그런 코드(예: 여러 차량을 한 트랜잭션에서
  같이 갱신하는 배치 작업)를 짤 때 왜 잠금 순서를 통일해야 하는지"를 미리 체감해두기 위한
  것이다.
