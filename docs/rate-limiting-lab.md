# POST /api/reservations Rate Limiting 실습

## 배경

인기 지점이 갑자기 풀리는 순간처럼, 짧은 시간에 동시 요청이 몰리는 스파이크 상황을
가정한다. 서버가 몰려드는 요청을 전부 받아서 처리하려고 하면(스레드 풀/DB 커넥션까지
큐잉), 개별 요청의 응답 시간이 전체적으로 늘어지면서 결국 모든 사용자가 느린 응답을
받게 된다. Rate limiting은 반대로 접근한다 — 미리 정해둔 처리 능력만큼만 받고, 그
이상은 즉시 429로 돌려보내 "받은 요청만큼은 빠르게 처리"하는 쪽을 선택한다.

## 구성

- Redis 기반 토큰 버킷(`TokenBucketRateLimiter` + `token_bucket.lua`) — 클라이언트(IP)별로
  독립된 버킷을 두고, `capacity`(버스트 허용량)만큼 순간적으로 받아준 뒤 `refill-per-second`
  속도로만 다시 채운다. "읽고 계산하고 쓰기"를 Lua 스크립트로 Redis 안에서 원자적으로
  실행해 동시 요청 간 경합(`docs/concurrent-booking-lab.md`의 check-then-act 레이스와 같은
  종류)을 원천적으로 막는다.
- `RateLimitFilter`(`OncePerRequestFilter`) — `POST /api/reservations`에만 적용. 버킷이
  비어있으면 `429 Too Many Requests` + JSON 에러 바디를 즉시 반환한다.
- 설정값: `capacity: 50`, `refill-per-second: 50` (`application.yml`).
- 적용 전/후 비교를 위한 토글: `app.rate-limit.enabled` (기본 `true`, 실습 시 `false`로
  끄고 비교).

## 실행 방법

```bash
# 적용 전(비교용)
APP_RATE_LIMIT_ENABLED=false ./gradlew :reservation-service:bootRun

# 적용 후(기본값)
./gradlew :reservation-service:bootRun

# 스파이크 테스트: 500명이 램프업 없이 거의 동시에 1건씩 요청
BASE_URL=http://localhost:8081 k6 run infra/k6/reservation-spike.js
```

`infra/k6/reservation-spike.js`는 재고가 부족한 지점(`branchId: 9999999999`)을 대상으로
500 VU가 `per-vu-iterations`(vus=500, iterations=1)로 사실상 동시에 요청을 1번씩 쏜다.
201/429 각각을 커스텀 Counter로 집계한다.

## 실제 실행 결과 (500명 동시 스파이크)

| | 적용 전 | 적용 후 |
|---|---|---|
| 성공(201) | 500 / 500 | 92 / 500 |
| 거절(429) | 0 / 500 | 408 / 500 |
| 성공 응답 평균 | 2.09s | 424.57ms |
| 성공 응답 p99 | **2.69s** | **487.87ms** |
| 성공 응답 max | 2.73s | 491.13ms |

(성공 요청 기준 레이턴시. 적용 전엔 500건 전부가 성공이라 "전체 = 성공"이고, 적용
후엔 성공한 92건만 집계했다 — 429는 Redis 확인만 하고 즉시 반환되므로 별도로 재도 보통
수 ms 수준이다.)

## 해석: "전부 받아내는 것" vs "서비스를 지키는 것"

적용 전은 500건을 전부 성공(201)시켰지만, 그 대가로 모든 요청의 응답이 함께 느려졌다
(p99 2.69초). Tomcat 스레드 풀과 DB 커넥션이 500개 요청을 동시에 붙잡고 처리하려다 보니,
뒤로 갈수록 요청이 대기열에 쌓이는 형태다 — 겉보기엔 전부 성공이라 "문제없다"고 보이지만,
실제로는 정상 처리 능력을 넘는 트래픽을 억지로 밀어넣은 것이고, 이 상태가 조금만 더
길게 가거나 요청이 조금만 더 몰렸다면 타임아웃/커넥션 고갈로 전체가 무너질 수 있는
상황이다.

적용 후는 토큰 버킷 용량(capacity=50)만큼만 즉시 처리하고 나머지 408건은 429로 빠르게
쳐냈다. 결과적으로 성공한 92건(버스트 처리량 50 + 요청 처리 시간 동안 재충전된 토큰)의
응답 시간은 424ms대로, 적용 전 평균(2.09s)보다 5배 가까이 빨라졌다. "500건 중 몇 건이라도
더 받아주자"가 아니라 "내가 감당할 수 있는 만큼만 받고, 그 안에서는 빠르게 처리해준다"는
선택이다.

어느 쪽이 맞는지는 도메인에 달려있다 — 429를 받은 클라이언트가 재시도하면 되는
상황(웹 UI에서 사용자가 버튼을 다시 누르는 정도)이라면 적용 후 쪽이 전체 시스템을
더 안전하게 지킨다. 반대로 모든 요청이 반드시 즉시 성공해야 하는 상황이라면 rate
limit보다 애초에 처리 용량(오토스케일링 등, `docs/autoscaling-lab.md`)을 늘리는 쪽으로
접근해야 한다.
