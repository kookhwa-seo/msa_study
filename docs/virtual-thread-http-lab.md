# 가상 스레드로 블로킹 호출 살리기

## 구성

`docs/blocking-vs-nonblocking-lab.md`의 `/blocking`(RestClient) 엔드포인트를 코드는 그대로 두고,
`spring.threads.virtual.enabled=true`만 켜서 Tomcat이 요청 처리에 플랫폼 스레드 풀 대신
**가상 스레드**를 쓰게 만들었다. `/blocking`이 내부에서 부르는 `RestClient`(JDK
`HttpClient` 기반)의 블로킹 I/O는 가상 스레드 위에서 실행되면 JDK 21이 자동으로 캐리어 스레드를
반납해준다(`vthread-lab` 실습에서 이미 확인한 것과 같은 메커니즘) - 그래서 애플리케이션 코드를
한 줄도 안 고쳤는데 동작 방식이 바뀐다.

## 실행 방법

```bash
SPRING_THREADS_VIRTUAL_ENABLED=true ./gradlew :http-client-lab:bootRun
BASE_URL=http://localhost:8088 TARGET_PATH=/blocking VU_COUNT=500 \
  k6 run infra/k6/http-client-comparison.js
```

## 실제 실행 결과 (3자 비교)

| 동시 사용자 | a) RestClient+플랫폼 스레드 | b) RestClient+가상 스레드 | c) WebClient(논블로킹) |
|---|---|---|---|
| 50  | 138.0 req/s, p99 504ms | 137.9 req/s, p99 506ms | 138.5 req/s, p99 503ms |
| 100 | 278.0 req/s, p99 502ms | 278.2 req/s, p99 503ms | 278.3 req/s, p99 502ms |
| 200 | 556.6 req/s, p99 501ms | 556.5 req/s, p99 503ms | 555.5 req/s, p99 501ms |
| **500** | **555.7 req/s, p99 1,040ms** | **1,384.0 req/s, p99 503ms** | **1,380.0 req/s, p99 505ms** |

200 이하에서는 세 방식이 사실상 똑같다(풀 크기 안에서는 애초에 아무도 못 넘어가는 병목이 없다).
**500명(풀 크기 초과)에서 a)만 무너지고, b)와 c)는 사실상 구분이 안 될 정도로 같다** — 가상
스레드로 바꾼 RestClient(1,384.0 req/s)가 WebClient(1,380.0 req/s)와 오차 범위 안에서 동일한
처리량을 냈고, p99도 둘 다 500ms대에 그대로 머물렀다.

## 왜 코드를 그대로 두고도 논블로킹과 비슷한 처리량이 나오는가

플랫폼 스레드는 "요청 하나 = 스레드 하나"가 응답이 올 때까지 고정으로 묶인다. 가상 스레드는
`Thread.sleep()`이나 블로킹 소켓 읽기처럼 "기다리는" 지점을 만나면, JDK가 그 가상 스레드를
캐리어(진짜 OS) 스레드에서 자동으로 떼어내(unmount) 다른 가상 스레드가 그 캐리어를 쓸 수 있게
해준다. 그래서 개발자는 여전히 "요청 하나당 스레드 하나"라는 익숙한 동기 코드를 그대로 쓰는데,
실제로는 응답을 기다리는 수백~수천 개의 가상 스레드가 소수의 진짜 OS 스레드(보통 CPU 코어 수
만큼)만 공유해서 쓴다 - WebClient가 이벤트 루프로 얻는 이점을, 가상 스레드는 "기다리는 동안
캐리어를 놓아준다"는 메커니즘으로 똑같이 얻는 셈이다.

## 그럼에도 WebClient와 남는 차이가 있다면 무엇 때문인가

이번 실측에서는 500명 구간의 TPS(1,384.0 vs 1,380.0)와 p99(503ms vs 505ms) 모두 0.5% 안쪽의
차이라, **실질적으로 차이가 없다**고 봐도 된다. 이 수치만 보면 "가상 스레드면 WebClient가
필요 없다"고 생각하기 쉬운데, 이 실습이 재고 있는 범위 밖에서 여전히 남는 구조적 차이가 있다:

- **가상 스레드는 "블로킹 코드를 값싸게 만드는" 것이지, 블로킹 코드를 논블로킹으로 바꿔주는
  게 아니다.** 예를 들어 "결제 승인 + 재고 확인 두 외부 API를 동시에 부르고 둘 다 끝나면
  합친다" 같은 진짜 동시 조합(`CompletableFuture.allOf`, WebFlux의 `Mono.zip` 등)은 리액티브
  스택이 원래 잘하는 영역이고, 가상 스레드로는 "스레드를 여러 개 만들어서 각각 블로킹으로
  기다리게" 하는 방식으로만 흉내낼 수 있다 - 여전히 동작은 하지만 설계 방식 자체가 다르다.
- **가상 스레드는 CPU-bound 구간에는 도움이 안 된다** (`vthread-lab` 실습에서 이미 확인:
  I/O-bound 27.7배 vs CPU-bound 1.09배). 이번 mock 서버 호출은 순수 I/O 대기라 가상 스레드가
  최대 효과를 보는 케이스였다 - 만약 응답을 받은 뒤 무거운 JSON 파싱/변환처럼 CPU를 실제로
  쓰는 작업이 섞여 있었다면 차이가 다시 벌어졌을 수 있다.
- **생태계 성숙도**: WebClient/Reactor는 백프레셔, 타임아웃, 재시도, 서킷 브레이커 같은 조합
  연산자가 이미 풍부하다. 가상 스레드는 JDK 21부터 생긴 기능이라, 같은 걸 하려면 기존
  블로킹 라이브러리(Resilience4j 등)를 그대로 쓰거나 직접 구현해야 한다.

결론적으로 "느린 외부 API 하나를 순서대로 기다렸다가 응답만 돌려주는" 이번 실습 같은 단순한
경우에는 가상 스레드가 코드 변경 없이 WebClient와 동등한 처리량을 낸다. 여러 외부 호출을
진짜로 동시에 조합해야 하거나 리액티브 생태계의 연산자가 필요한 복잡한 경우라면 여전히
WebClient/리액티브 스택이 유리하다.
