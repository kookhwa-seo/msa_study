# 가상 스레드(Virtual Thread) vs 플랫폼 스레드 벤치마크

## 왜 하는 실습인가

"Java의 블로킹 I/O 모델이 Node.js 같은 이벤트 루프 기반 모델보다 대량 동시 연결 처리에
불리한가?"라는 질문에서 출발했다. 전통적인 Java는 요청 하나당 OS 스레드(플랫폼 스레드) 하나를
점유하는 모델이라, 블로킹 I/O(DB 조회, 외부 API 호출 등) 동안 그 스레드가 통째로 묶인다 — 그래서
동시 요청이 스레드 풀 크기(보통 수백 개)를 넘으면 나머지는 무조건 대기열에서 기다려야 한다.
JDK 21의 가상 스레드가 정확히 이 문제를 겨냥한 기능이라는 건 알고 있었지만, "왜/얼마나" 유리한지
직접 재본 적은 없어서 벤치마크로 확인했다.

## 코드 위치

`vthread-lab` 모듈(`vthread-lab/src/main/java/com/msastudy/vthreadlab/VirtualThreadLabRunner.java`).
Spring/Tomcat 없이 순수 `java.util.concurrent`만 쓴다 — 프레임워크 레이어(커넥션 풀, 톰캣 스레드
풀 설정 등)를 끼우면 "가상 스레드 자체의 차이"를 보기 어려워지기 때문. `kafka-lab`/`deadlock-lab`과
같은 원칙.

## 실습 설계

두 가지 워크로드를 각각 "플랫폼 스레드 풀(크기 200 — Spring Boot 내장 Tomcat의 기본
`server.tomcat.threads.max`와 동일하게 맞춤)"과 "가상 스레드(작업당 1개)"로 돌려서 비교한다.

- **I/O-bound**: 작업 10,000개, 각각 `Thread.sleep(50)`으로 "DB/외부 API 호출 한 번"을 흉내낸다.
  실제 I/O 없이 sleep으로 흉내낸 이유는, 진짜 네트워크 호출을 쓰면 그 대상 서버의 처리 속도가
  변수로 섞여서 "스레드 모델 자체의 차이"를 순수하게 보기 어렵기 때문이다.
- **CPU-bound**: 작업 2,000개, 각각 3만 이하의 소수 개수를 시행 나눗셈으로 센다(일부러 비효율적
  으로 무거운 진짜 CPU 연산). 결과 합계를 매번 출력해서 JIT이 "안 쓰는 계산"이라고 판단해
  통째로 스킵(dead code elimination)하지 않았다는 걸 확인할 수 있게 했다.

## 실행 방법

```bash
./gradlew :vthread-lab:run
```

## 실제 실행 결과

```
CPU 코어 수(availableProcessors): 10

==================== I/O-bound (작업당 50ms 블로킹 sleep, 10000개 작업) ====================
[플랫폼 스레드 (풀 크기 200)] 10,000개 작업 완료, 총 2,691ms 소요
[가상 스레드 (작업당 1개)] 10,000개 작업 완료, 총 97ms 소요

==================== CPU-bound (작업당 30000 이하 소수 개수 세기, 2000개 작업) ====================
[플랫폼 스레드 (풀 크기 200)] 2,000개 작업 완료, 총 162ms 소요 (sanity sum=6,490,000)
[가상 스레드 (작업당 1개)] 2,000개 작업 완료, 총 148ms 소요 (sanity sum=6,490,000)

==================== 결과 요약 ====================
I/O-bound  : 플랫폼 2,691ms  vs  가상 97ms  (27.7배)
CPU-bound  : 플랫폼 162ms  vs  가상 148ms  (1.09배)
```

## 왜 이런 숫자가 나오는가

**I/O-bound (27.7배 차이)**: 플랫폼 스레드는 풀 크기가 200으로 고정돼 있어서, 10,000개 작업을
한 번에 200개씩만 처리할 수 있다 — 50개 배치 × 50ms = 이론상 2,500ms, 실측 2,691ms로 거의
정확히 들어맞는다. 가상 스레드는 `Thread.sleep()`으로 블로킹되는 순간 OS 스레드(캐리어 스레드,
보통 CPU 코어 수만큼)를 반납하기 때문에, 10,000개를 사실상 동시에 "재워"놓고 50ms 뒤 한꺼번에
깨울 수 있다 — 그래서 총 소요 시간이 200개씩 나눠 처리한 것의 합이 아니라 **작업 1개의 지연시간
(50ms)에 근접**한다(스케줄링 오버헤드를 더해 97ms).

**CPU-bound (1.09배, 거의 차이 없음)**: 이 컴퓨터는 코어가 10개다. 어떤 스레드 모델을 쓰든,
동시에 진짜로 계산을 수행할 수 있는 스레드는 물리적으로 코어 수(10개)를 넘을 수 없다. 가상
스레드는 "블로킹(대기)되는 동안 캐리어 스레드를 반납"하는 게 핵심 이점인데, CPU 연산은 애초에
블로킹되는 구간이 없으니 이 이점이 발휘될 자리가 없다. 그래서 두 모델의 처리 시간이 거의
같다(플랫폼이 살짝 더 느린 건 200개 스레드 사이의 컨텍스트 스위칭 비용 때문으로 보인다).

## 결론 / 실무 연결

- 가상 스레드는 **"I/O로 기다리는 동안 OS 스레드를 낭비하지 않는다"**는 것이 핵심이지,
  "연산 자체를 더 빠르게 해준다"는 게 아니다. CPU-bound 작업에는 아무 이점이 없다 — 오히려
  가상 스레드를 CPU-bound 작업에 무분별하게 쓰면(예: 가상 스레드로 무거운 연산을 수천 개
  동시에 던지기) 코어 수만큼만 진짜로 실행되고 나머지는 그냥 대기하니, 오히려 스케줄링
  오버헤드만 늘 수 있다.
- Java가 전통적으로 Node.js 같은 이벤트 루프 모델보다 "대량 동시 연결"에 불리했던 진짜 이유는
  "블로킹 I/O를 쓴다는 것" 자체가 아니라, **블로킹되는 동안 OS 스레드(무겁고 개수가 제한적인
  자원)를 계속 점유했다는 것**이었다. 가상 스레드는 Node의 논블로킹/이벤트 루프 모델처럼
  코드를 콜백/Promise/reactive 스타일로 다시 짤 필요 없이, **기존의 평범한 블로킹 코드 그대로**
  이 문제를 해결한다 — `Thread.sleep()`/JDBC 호출을 그대로 써도 되고, 다만 실행 주체를 플랫폼
  스레드에서 가상 스레드로 바꾸기만 하면 된다(Spring Boot 3.2+는 `spring.threads.virtual.enabled:
  true` 한 줄).
- 이 프로젝트의 서비스들(REST API + JPA/JDBC 호출)은 전형적인 I/O-bound 워크로드라, 이 실습의
  27.7배 차이가 시사하는 이점을 그대로 받을 수 있는 후보다. 다만 지금은 트래픽 규모가 작아서
  기본 플랫폼 스레드 풀로도 병목이 없기 때문에, 실제로 켜서 이득을 보려면 먼저 "동시 접속이 풀
  크기(200)를 넘는 트래픽"이 실제로 있는지부터 확인해야 한다 — 병목이 없는 곳에 최적화를
  적용해봐야 체감 차이가 없다.
